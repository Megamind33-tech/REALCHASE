# CHASE Studio Pro — Performance & Stress Report (Milestone 9)

This document describes the performance / stress smoke test added in Milestone 9,
the metrics it measures, the thresholds chosen, and how to run it. All numbers in
this report are sampled from a real run of the app under load — none are
fabricated. Where the headless environment cannot produce GPU-representative
numbers, that is called out explicitly.

## What is tested

The test (`tests/perf-stress-smoke.mjs`) drives the **real** CHASE Studio Pro
application (the Babylon.js virtual studio) through a sustained-load scenario and
samples live runtime metrics off the running page. It is a Playwright test in the
same style as the other `tests/*.mjs` smoke tests (`anti-demo-smoke`,
`browser-visual-smoke`, `source-manager-smoke`, `output-preview-smoke`).

### Stress scenario

1. **Scene population** — imports the three real glTF binary fixtures in
   `tests/fixtures/` (`chase-test-cube.glb`, `chase-test-pyramid.glb`,
   `chase-test-octa.glb`, generated by `node tools/make-test-glb.mjs`) through
   the actual builder import control (`data-testid="asset-file-input"`). The
   import is repeated for several rounds (`CHASE_PERF_IMPORT_ROUNDS`, default 3)
   so the scene accumulates many meshes/materials. Each round asserts the
   imported assets actually appear in the scene outliner
   (`[data-testid^="outliner-asset-"]`), so we know the geometry is really in the
   Babylon scene and not silently dropped.
2. **Camera cycling** — round-robins through all six studio cameras
   (`camera-thumb-cam1` … `camera-thumb-cam6`) by clicking the real camera-strip
   thumbnails, forcing view changes and re-renders.
3. **Quality-profile churn** — periodically switches the quality profile between
   `low` / `balanced` / `high` (the `QUALITY_PROFILES` from
   `src/engine/qualityProfile.ts`) to exercise engine re-configuration paths
   (hardware scaling, shadow map size, MSAA, post-process toggles).
4. **Sustained sampling** — over a fixed window (`CHASE_PERF_DURATION_MS`,
   default 20s) it samples on a fixed cadence (`CHASE_PERF_SAMPLE_INTERVAL_MS`,
   default 500ms).

### Metrics measured (all real)

- **FPS** — read from the engine's own readout that the app renders into the
  status bar (`StatusBar.tsx` renders `` `${metrics.fps} fps` ``). The test parses
  the live DOM text (`/(\d+(?:\.\d+)?)\s*fps/i`) every sample. This is the
  engine's real measured frame rate (`engine.getFps()` surfaced through shell
  state), not a synthetic counter.
- **JS heap** — `performance.memory` (`usedJSHeapSize` / `totalJSHeapSize` /
  `jsHeapSizeLimit`) sampled each tick when the browser exposes it (Chromium
  does). Start/end/peak used-heap are recorded to spot gross leaks across the run.

### Assertions

- The page never crashes (`page.on('crash')`) and emits no uncaught page errors
  (`page.on('pageerror')`).
- The engine reaches a ready state and publishes a numeric FPS readout (the test
  waits for the first `<n> fps` to appear, up to 120s).
- Imported assets actually land in the scene outliner each import round.
- **Median FPS over the run stays above a floor** (`CHASE_PERF_MIN_FPS`,
  default 5). See "Thresholds" for why the default is low.

On any failure the test exits non-zero. A metrics JSON log and a full-page
screenshot are always written to `docs/evidence/phase-9/`
(`perf-stress-metrics.json`, `perf-stress-builder.png`), including on failure, so
the captured numbers are inspectable either way.

## Thresholds chosen

The default median-FPS floor is **5 fps**. This is deliberately conservative
because the test is designed to also pass in **headless software-WebGL**
environments: with no real GPU, Chromium falls back to SwiftShader (software
rasterization via ANGLE), which is one to two orders of magnitude slower than
hardware rendering. The floor exists to catch a **hard regression / stall**
(engine wedged at ~0 fps, render loop dead, crash), not to certify a target
frame rate.

On a GPU-backed runner the floor should be raised — e.g. `CHASE_PERF_MIN_FPS=45`
for a 60fps target with headroom. Every tunable is overridable via environment
variable so CI on capable hardware can tighten the gate without code changes:

| Env var | Default | Meaning |
| --- | --- | --- |
| `CHASE_PERF_MIN_FPS` | `5` | Minimum acceptable **median** FPS over the run |
| `CHASE_PERF_DURATION_MS` | `20000` | Sustained stress window |
| `CHASE_PERF_SAMPLE_INTERVAL_MS` | `500` | Sampling cadence |
| `CHASE_PERF_IMPORT_ROUNDS` | `3` | GLB import rounds (scene load factor) |
| `CHASE_VISUAL_BASE_URL` | `http://127.0.0.1:1420` | App URL |
| `CHASE_CHROMIUM_EXECUTABLE` | (Playwright default) | Chrome/Chromium binary |
| `CHASE_CHROMIUM_ARGS` | swiftshader set (below) | Override Chromium launch args |
| `CHASE_PERF_NO_SERVER` | (unset) | Require an external server; don't auto-boot |

Default Chromium args force software WebGL so Babylon renders headlessly:
`--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader
--ignore-gpu-blocklist`.

## How to run

The test is self-contained: if nothing is listening at the app URL it will run
`npm run build` and start `vite preview` on port 1420 itself, then tear the
server down afterwards.

```bash
# Self-contained (build + preview + stress):
npm run test:perf-stress

# Against an already-running server (e.g. `npm run dev`), skip auto-boot:
CHASE_PERF_NO_SERVER=1 npm run test:perf-stress

# Point at a specific Chromium binary (headless CI):
CHASE_CHROMIUM_EXECUTABLE=/path/to/chrome npm run test:perf-stress

# Tighten the gate on a GPU runner:
CHASE_PERF_MIN_FPS=45 CHASE_PERF_DURATION_MS=30000 npm run test:perf-stress
```

Evidence is written to `docs/evidence/phase-9/`.

### Environment caveat (software WebGL)

Like the other browser smoke tests in this repo (see
`docs/evidence/phase-2/browser-visual-smoke/`), the CI/headless environment used
here has **no GPU**: WebGL is served by SwiftShader (software rasterization).
SwiftShader frame rates are **not** representative of end-user performance on a
real GPU — they are dramatically lower. The numbers captured below therefore
demonstrate that the engine *renders correctly, stays alive under load, and does
not leak or crash during sustained churn*; they are a **stability / regression
floor**, not a performance benchmark. To obtain representative FPS numbers, run
this same test on a machine with hardware-accelerated WebGL and raise
`CHASE_PERF_MIN_FPS` accordingly.
